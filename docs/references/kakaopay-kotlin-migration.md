# 카카오페이 — 자바 프로젝트 3개 코틀린 점진적 전환기 (2023-12-05)

- 출처: 카카오페이 기술 블로그, "자바 프로젝트 3개 코틀린 점진적 전환기", 2023-12-05, 해외결제 백엔드 — https://tech.kakaopay.com/post/kotlin-migration/
- 정리: 2026-10-14, Phase 3.7

## 요지

- **전환 순서**: 엔티티·리포지토리·유틸 → 컨트롤러 → 서비스
- **안전망**: 전환 전 테스트 강화뿐. 운영 트래픽 재생·사이드이펙트 비교는 없고, 전환 중 발생한 이슈 수는 보고되지 않음
- **함정**: 자동 변환(IntelliJ Java→Kotlin) 후 **nullable 오판**
- **규모·기간**: 1,100 파일, 2.5개월, 3명. Java·Kotlin 혼재 상태로 운영하며 1년 뒤 80~90% 전환
- **기타**: git rename 이력 보존 필요(파일 확장자 변경이 삭제+추가로 기록되지 않게)

## 이 프로젝트에 반영

| 요지 | 반영 |
|---|---|
| nullable 오판이 대표 함정 | **F0(sku nullability) 현업 근거** — Legacy 409 / Kotlin 400(findings O6). 이 프로젝트는 그 차이를 행동 Evidence로 실측했다 |
| 전환 순서 엔티티·리포지토리 → 컨트롤러 → 서비스 | 사다리 순서 비교: 이 프로젝트는 클라이언트(v1.1) → 엔티티·리포지토리(v1.2) → 서비스(v1.3) → 컨트롤러(v1.4). 엔티티를 이른 단계에 둔 점은 같고, 서비스·컨트롤러 순서는 반대 |
| 안전망 = 테스트 강화, 트래픽·사이드이펙트 비교 없음 | "현업 전환 검증 = 테스트 커버리지"라는 서술의 근거(우아한형제들 2025와 묶어서). 이 프로젝트의 차등 검증(미러 트래픽 + 사이드이펙트 Evidence)이 보완하는 지점 |
| 혼재 상태로 1년 운영 | Phase 4 전제: 혼재 코드베이스에서 변경 클래스 → 영향 API 스코핑 |
| git rename 이력 보존 | Phase 4 변경 클래스 추출은 `git diff -M`(rename 감지), 사다리·결함 브랜치 squash 금지(call-graph.md 메모) |
