## 0. 결정 필요 사항

**D-4.3a 4.4 `tags.json`의 inScope 입도 — 4.4 구현 전에 필요 (findings O19)**

계획은 Tag 순위 품질을 "비-SAME pair가 inScope 구간에 든 비율(= Recall)"로 정의한다. `= Recall`이면 세션 입도다. 그런데 D-4.1b는 "요청 단위 차이는 Tag에서 드러난다"를 전제로 했고, 이는 요청 입도여야 성립한다. 두 입도가 실제로 갈리는 변형이 있다.

| 입도 | inScope | F7 예산·비-SAME 포함 | F7 외 결함 8개 포함 |
|---|---|---|---|
| 세션 (계획 정의) | 선택 세션의 모든 pair | 66.1%·**2/2** | 전부 1.0 |
| 요청 | `impactedRequests`의 pair | 22.0%·**1/2** | 전부 1.0 |

F7의 R000042는 `PaymentGatewayClient`를 실행하지 않는 후속 `order.get`이지만 앞 요청 R000041의 실패가 상태로 전파돼 CV가 됐다. 이번 평가는 두 입도를 모두 계산했고, 4.4 run 대상(F8·F3)은 어느 입도든 1.0이다.
- **(A) 권장**: `inScope`는 **세션 입도**(계획 정의 그대로, 끝난 기준 "비-SAME pair가 모두 inScope 구간 안" 유지). `tags.json`에 요청 입도 근거 `impactedRequest: bool`을 함께 두고 리뷰 순서를 **영향 요청 → 같은 세션의 나머지 → 범위 밖** 3단으로 한다. 요청 입도 수치는 보조로 보고
- (B) `inScope`를 요청 입도로 바꾼다. 예산이 줄지만(F7 66% → 22%) 비-SAME을 앞 구간 밖으로 놓칠 수 있다(F7 1/2). 4.4 끝난 기준 문구의 재해석이 필요

## 5. 지시와 다르게 구현한 것

- **Tag를 두 입도로 계산**: 계획 정의는 세션 입도(= Recall)이고 D-4.1b는 요청 입도를 전제한다. 둘 다 내고 4.4 결정은 0절에 올렸다. 새 지표를 만든 것이 아니라 같은 지표의 inScope 기준 두 가지다
- **v1.x 감소율 분모 48**: 사다리 run은 corpus v2(46요청, S011 없음)로 돌았지만 감소율은 계획대로 corpus v2.1의 48 기준이다. Tag 예산은 그 run의 58 pair 기준이라 F 변형과 분모가 다르다(`phase4-metrics.json`)
- **`evaluate.py`가 `impact.compute`를 호출**: ablation은 맵만 바꿔 같은 규칙을 돌리려고 그렇게 했다. 엔진 import는 아니다
- **ablation은 impact-v1.1만**: v1.0 나란히 표기는 정본 지표(결과표)에 적용했다
- **`test_skeleton_clis_exit_2` 삭제**: 골격이 끝나 대상이 없다

## 6. 문제·해결·남은 한계

- **세션 단위 선택이 필요한 실례(O19)**: F7 R000042. 요청 단위 Filter였다면 놓쳤다. O15의 "세션 단위 선택이 덮는다"에 대한 실측 근거다
- **Recall 1.0은 corpus 안에서의 값이다**: 비-SAME이 corpus로 관측된 것만 분모에 든다. 변형 9·세션 11로 일반화하지 않는다
- **B2-S 평균은 세션별 diff 수로 가중된다**: F1·F4처럼 diff가 한 세션에 몰리면 Recall 1.0 비율이 평균과 같아지고, F2·F3처럼 흩어지면 최소가 높아도 1.0 비율은 낮다. 평균만 보지 말고 1.0 비율을 함께 본다
- **스코핑의 이득 차이는 B2-S에서 변경 지역성에 따라 다르다**: F3(0.003)은 스코핑이 7세션 전부를 맞힌 경우이고, F4(0.818)는 무작위 9세션도 대개 맞히는 경우다
- **Filter 하 run 범위 판정은 아직 없다**: 4.4에서 확인
